# JIT アーキテクチャ詳細ルール

## JIT コンパイルの基本概念

Webschembly の最大の特長は、ブラウザ(Wasm)上で動作する Scheme の JIT (Just-In-Time) コンパイラである点です。
Rust で記述されたコンパイラ自体が Wasm にコンパイルされており、実行時に Scheme コードの中間表現 (IR) をもとに、特化された新たな WebAssembly モジュールを動的に生成します。

## 1. 段階的コンパイル (Tiered Compilation) と単位

JIT コンパイルは、実行時のプロファイル情報に基づいて段階的に行われます。

- **モジュール単位 (AOT / 初期ロード)**:
  初期ロード時、ソースコードはパースされ IR に変換されます。この時点ではスタブ(未パース/未最適化を示す軽量なコード)が生成される場合があります。
- **関数レベルJIT (`instantiate_func`)**:
  クロージャが呼び出された際、その関数全体を JIT コンパイルします。環境(Env)に含まれる型情報などを用いて、そのクロージャに特化した最適化を行います。
- **ベーシックブロックレベルJIT (`instantiate_bb`)**:
  関数内の制御フローが巨大な場合、さらに細かくベーシックブロック単位で JIT コンパイルを行うことが可能です。

## 2. プロファイル駆動最適化 (PGO) と動的パッチ

実行時の動的な挙動をプロファイリングし、ホットスポットを最適化します。

- **ブランチカウンタ (`increment_branch_counter`)**:
  条件分岐などの特定のパスが実行された回数をカウントします。閾値を超えた(ホットになった)場合、そのパスに特化した再コンパイルをトリガーします。
- **動的パッチ (`MutFuncRef`)**:
  Wasm の関数ポインタは不変ですが、再 JIT された関数に切り替えるため、Webschembly では `MutFuncRef` (`(mut funcref)` を持つ GC struct) を使用します。これにより、JIT が新しい最適化済み Wasm 関数を生成した際、ポインタの中身を書き換えるだけで、すべての呼び出し元が即座に新しいコードを参照するようになります。

## 3. 型特殊化 (Type Specialization)

クロージャが実行される際、JIT コンパイラはそのクロージャがキャプチャしている環境 (`Env`) を検査します。
環境内の変数が特定の型(例: 整数 `Int` やベクタ `Vector`)で固定されていると判定できた場合、不要な `ToObj`/`FromObj` 型チェックを省略した、その型専用の高速な Wasm 命令列を生成します。

## 4. Block Fusion (ブロック結合最適化)

WebAssembly における関数呼び出しのオーバーヘッドを削減するための独自最適化です。
細分化されたベーシックブロック(BB)を Wasm の関数として独立させると呼び出しコストが嵩むため、複数の BB を単一の Wasm 関数に統合(Fuse)します。

- **SmallFusion**: 小規模なブロック群を結合。
- **LargeFusion**: 可能な限り広範囲のブロックを一つの関数に結合し、Wasm ランタイム側の最適化(V8のTurbofan等)がより効率的に働くようにします。

## 5. JavaScript との動的リンク連携

JIT コンパイラが Wasm 内で新しいバイナリを出力すると、JS 側の `js_instantiate` コールバックが同期的に呼び出されます。
JS 側では `WebAssembly.Module` を即座にインスタンス化し、生成された関数のエクスポートを共有の `dynamic` オブジェクトに `Object.assign` でマージします。Wasm 側はこの `dynamic` オブジェクトをインポートしているため、動的に追加された関数をシームレスに呼び出すことができます。

## 6. JIT の可視化

JIT コンパイラの内部状態変化（ブロックのコンパイル状況、スタブからの置き換え等）は `JitLogEvent` として JSON 化され、JS 側にストリーム送信されます。
Playground の `JitGraph.tsx` では、このログを用いて関数・ベーシックブロックの依存関係とJITの進行状況をリアルタイムで有向グラフとして可視化します。
